# Воспроизведение инцидента EX-1001

## Контекст

**Инцидент 2026-04-29.** Заказ `17747836`, транзакция `17746275`, `payment_system=10` (FreedomPay):

- В БД PG транзакция в `StatusFailed`, `response_data.error = ": не удалось провести оплату: Неверный статус платежа"`.
- В банкинге Freedom: `pg_payment_id=1753769848`, статус `success`, **деньги списаны 9 504 KZT** с карты `4400 43•• •••• 5744` (Kaspi Bank).

## Корневая причина

В PG flow saved-card оплаты: `init` → `hold`. См. ``merchant.go::Pay``.

```
ctx = smarthttp.WithRetryRequest(ctx)            // ← HTTP retry поверх hold
hl, errHold := merchant.Hold(ctx, holdCMD)
```

Сценарий рассинхрона:

1. `holdInit` → Freedom создал `pg_payment_id`.
2. `hold` ушёл в Freedom, деньги захолдированы, но **ответ потерялся** (сеть, краткий 5xx).
3. `smarthttp.WithRetryRequest` повторил запрос.
4. На повторе Freedom отвечает `pg_failure_description = "Неверный статус платежа"` — нельзя дважды захолдировать.
5. PG считает это фатальной ошибкой → транзакция `failed`.
6. Параллельно прилетает webhook `success`, но `MarkAsAuthorized` из `failed` запрещён state-machine.

**Итог:** правда в PSP, у нас — fail. Деньги списаны, заказ закрыт неуспехом.

## Решение в PG (ветка EX-1001)

`ReconcilingClient` оборачивает `Freedom.Pay`. При ошибке:

1. `ErrorClassifier` смотрит на текст ошибки. Если содержит `"Неверный статус платежа"` → `OutcomeAmbiguous`.
2. Делается один read-only `Status` к PSP.
3. Если PSP вернул `Authorized/success` → транзакция всё-таки успешна, лог `reconciliation: recovered payment from false fail` (Warn — главный алерт).

Подробности: ``temp/reconciliation/README.md``.

## Воспроизведение через мок

### Способ 1 (автоматический, без сценариев)

Любой повторный `direct` на одном и том же `pg_payment_id` мок отдаёт `Неверный статус платежа` — это и есть инцидент. Достаточно симулировать retry в PG.

```bash
# 1) HoldInit
curl -X POST http://localhost:48532/v1/merchant/100001/card/init \
  -H "Content-Type: application/x-www-form-urlencoded" \
  --data-urlencode 'pg_xml=...'  # с валидной подписью
# → pg_payment_id=1700000001

# 2) Hold (ok)
curl ... /v1/merchant/100001/card/direct ...   # pg_status=ok, Authorized

# 3) Hold ещё раз (retry-симуляция) → ambiguous!
curl ... /v1/merchant/100001/card/direct ...   # pg_failure_description="Неверный статус платежа"
```

В реальном PG это происходит само из-за `smarthttp.WithRetryRequest`. Достаточно: настроить ENV (см. ниже), триггернуть оплату — retry даст ambiguous, ReconcilingClient увидит Authorized в `Status`.

### Способ 2 (через панель — детерминированный)

   - на следующий `get_status3.php` → `force_status: success`
3. Триггернуть оплату saved-card в PG (rahmet-app или curl-ом order/authorize).

5. Проверить лог:


### Способ 3 (мануально без double-scenario)

Один сценарий: matcher=`endpoint=direct, paymentID=*`, action=`ambiguous_error`, ConsumeOnce=true.

1. На свежей записи в `NEW` нажать `Force Authorized` → состояние Authorized.
2. PG идёт на Hold → срабатывает сценарий → ambiguous.
3. PG → Status (нет сценария) → мок отвечает реальным состоянием — `pg_payment_status=success` (потому что мы Force-Authorized).
4. Recovery в PG.

## Настройка PG-стороны (один раз)

### 1. Локальное перенаправление PG → mock

В `pkg/freedompay/freedompay.go` хосты `api.freedompay.kz` и `customer.freedompay.kz` зашиты как константы. Мы добавили оверрайд через ENV. В `.env` локального PG:

```
FREEDOM_PAY_HOST=http://chaospay:8532
FREEDOM_PAY_CUSTOMER_HOST=http://chaospay:8532
```

Без этого PG будет ходить на реальные хосты, мок не получит запросы.

### 2. Тестовый Freedom-терминал в БД PG

Значения должны совпадать с `CHAOSPAY_FREEDOM_MERCHANT_ID` / `CHAOSPAY_FREEDOM_SECRET`:

```bash
./payment-gateway terminal freedom \
  --terminalID=1 \
  --merchantID=100001 \
  --merchantSecret=mock-secret-key
```

### 3. Перезапустить PG

```bash
docker restart payment-gateway-go-backend
```

## Чистый рассинхрон без recovery

Иногда нужно проверить **обратный** сценарий: что произойдёт, если ReconcilingClient не среагирует и транзакция уйдёт в `failed`, а банк деньги списал. Это исходное состояние инцидента до фикса. Полезно для:

- Тестов мониторинга/алертов на «лежащие» failed-транзакции
- Тестов background `payment_status_checker`
- Тестов поведения webhook'а на терминальной транзакции

### Способ 1: preset «💸 Bank charged, PG failed»

1. [`/panel?tab=scenarios`](http://localhost:48532/panel?tab=scenarios) → нажми **💸 Bank charged, PG failed**. Создаётся consume-once сценарий: `direct → force_failure` с сообщением `"технический сбой банка"`.

   ⚠️ Сообщение **НЕ содержит** «Неверный статус платежа» — поэтому `ErrorClassifier` отклассифицирует ошибку как `OutcomeFatal`, ReconcilingClient НЕ полезет в Status, транзакция уйдёт в `failed`.

2. Триггерь оплату saved-card в PG.
3. Поток:

```
PG → init                 → мок: создаёт PaymentRecord (NEW)
PG → direct               → срабатывает scenario → "технический сбой банка"
PG → ErrorClassifier      → OutcomeFatal (нет ambiguous-marker)
PG → транзакция failed
                            мок: PaymentRecord остался NEW
```

4. **Сейчас** на свежей записи в `/panel?tab=cards` нажми **Force Captured** (или сначала **Force Authorized**, потом **Force Captured**). Это эмулирует «банк всё-таки списал деньги».

5. Имеем: `orders/pg = failed`, `mock-bank = CAPTURED`. Деньги «списаны» в банке, у нас ошибка оплаты. **Это и есть классический рассинхрон до EX-1001 фикса.**

### Способ 2: проверить, что webhook не лечит терминальный fail

После шага 5 нажми **Send Webhook** на CAPTURED-записи (с `result=ok`). Webhook долетит до PG, PG увидит `pg_result=1` и попытается перевести транзакцию в `Authorized`/`Captured`. Но state-machine блокирует переход из `failed` → ничего не меняется. В логах PG будет ошибка вроде `cannot transition from failed`.

Это второй кусок инцидента: даже если банк потом подтвердит платёж webhook'ом, мы не можем починиться сами. Нужен либо ручной аудит, либо отдельный recover-механизм.

### Способ 3: вручную, без сценариев — самый чистый

1. На вкладке `/panel?tab=cards` нажми **Add Test Payment** с `Status=CAPTURED`, любым `Order ID`, `Amount=1500`. Это «банк уже списал».
2. Заметь `Payment ID` (например `1700000005`).
3. С хоста или через PG-flow дёрни `direct` для этого `paymentID`. В моке handler [Hold](../internal/application/pay/service.go) увидит, что запись уже в `Authorized`/`Captured`, и вернёт `ErrAlreadyAuthorized` → handler транслирует в XML `pg_failure_description="Неверный статус платежа"`.

Если это в PG идёт через ReconcilingClient — будет recovery (Status вернёт `success`). Если хочешь без recovery, добавь сценарий `get_status3.php → force_status: failed` ПЕРЕД триггером — Status соврёт что fail → ReconcilingClient доверит банку → транзакция уйдёт в `failed`.

## Контракт «не сломать»

Строка `Неверный статус платежа` — это **контракт между моком и `error_classifier.go`**. Если её изменить (или сломать сериализацию через invalid_signature scenario без особой причины) — ReconcilingClient просто пройдёт мимо: PaymentError классифицируется как `OutcomeFatal` и транзакция уйдёт в `failed`.

Если в проде появится новая ambiguous-фраза — добавить и в ``error_classifier.go::ambiguousMarkers``, и параметром `message` в default ambiguous_error scenario.
